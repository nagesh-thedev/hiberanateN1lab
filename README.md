# Hibernate N+1 Query Lab

A hands-on Spring Boot project demonstrating the Hibernate N+1 query problem and two fetching strategies: JPQL `JOIN FETCH` and JPA `@EntityGraph`.

The lab uses a Department–Employee relationship to compare SQL generated by Hibernate and observe how repository fetching choices affect the number of queries executed.

## Problem Statement

When an API loads multiple departments and then accesses each department's employees, Hibernate's lazy loading can trigger an additional query for every department. This is the **N+1 query problem**.

In this lab, the API exposes three endpoints so the approaches can be tested and compared.

## Tech Stack

- Java 17
- Spring Boot
- Spring Data JPA / Hibernate
- MySQL
- Maven
- JUnit 5 and Mockito for service-layer unit tests

## Data Model

The sample database contains three departments and nine employees:

| Department | Employees |
|---|---:|
| Engineering | 3 |
| Human Resources | 3 |
| Finance | 3 |
| **Total** | **9** |

The `Department` entity has a one-to-many relationship with `Employee`. The collection is configured for lazy loading in the baseline implementation.

## API Endpoints

Base URL: `http://localhost:8080/api`

| Endpoint | Strategy | Purpose |
|---|---|---|
| `GET /departments/v1` | Baseline `findAll()` | Demonstrates the lazy-loading baseline when the employee collections are accessed |
| `GET /departments/v2` | JPQL `JOIN FETCH` | Fetches departments and employees using an explicit fetch join |
| `GET /departments/v3` | `@EntityGraph` on inherited `findAll()` | Applies an entity graph to fetch the `employee` relationship |

### Example requests

```bash
curl http://localhost:8080/api/departments/v1
curl http://localhost:8080/api/departments/v2
curl http://localhost:8080/api/departments/v3
```

Each endpoint returns a JSON list of departments, with employee details included. `Employee.department` is ignored in JSON serialization to avoid a bidirectional serialization loop.

## Fetching Strategies

### v1 — Lazy-loading baseline

The service calls the inherited repository `findAll()` method. When the API response accesses each department's lazy employee collection, Hibernate may issue additional SQL queries.

### v2 — `JOIN FETCH`

The repository uses explicit JPQL:

```java
@Query("SELECT d FROM Department d JOIN FETCH d.employee")
List<Department> findAllwithEmployeesByJoinFetch();
```

This fetch join requests departments and their employees in one query. Because it uses an `INNER JOIN`, departments without employees would not be included in this result.

### v3 — `@EntityGraph`

The repository applies an entity graph to the inherited `findAll()` method:

```java
@EntityGraph(attributePaths = {"employee"})
List<Department> findAll();
```

`@EntityGraph` specifies the relationship to fetch for this repository operation without requiring a custom JPQL query. In the observed SQL for this lab, Hibernate generated a `LEFT JOIN`, which can retain departments that have no employees.

## Observed Results

The following counts are from the SQL logs observed during this lab run, using the current sample data and endpoint behavior.

| Approach | SELECT statements observed | Observed SQL |
|---|---:|---|
| v1 — Lazy-loading baseline | 4 | One department query plus three employee queries |
| v2 — `JOIN FETCH` | 1 | One query using an `INNER JOIN` |
| v3 — `@EntityGraph` | 1 | One query using a `LEFT JOIN` |

Both optimized approaches returned the expected three departments and nine employees in the tested request.

> These are observations from this dataset and test run, not universal performance guarantees. Query count alone does not measure total execution time or prove which approach is fastest in every application.

## Repository Method Naming Lesson

During implementation, a custom method name such as `findAllWithEmployee()` caused a startup error similar to:

```text
No property 'findAllWithEmployee' found for type 'Department'
```

The lesson was that `@EntityGraph` controls the fetch plan; it does not make an arbitrary repository method name into a valid derived query.

Two approaches were explored:

1. Add an explicit `@Query` to define the JPQL for a custom method.
2. Apply `@EntityGraph` to the inherited `findAll()` method, avoiding a custom derived-query name.

The final v3 endpoint uses the second approach.

## Testing

The service-layer unit tests use JUnit 5 and Mockito to test service behavior without connecting to MySQL:

- When the repository returns three departments, the service returns those departments.
- When the repository returns an empty list, the service returns an empty list.

These unit tests verify service behavior. They do not, by themselves, prove Hibernate's generated SQL or query count; those were observed separately through SQL logging.

## SQL Logging

To inspect Hibernate SQL during local development, enable SQL logging in `application.properties`:

```properties
spring.jpa.show-sql=true
logging.level.org.hibernate.SQL=DEBUG
```

Use the logs while calling each endpoint to compare the statements generated by Hibernate.

## Run Locally

1. Clone this repository.
2. Configure your MySQL connection and credentials in your local application configuration. Do not commit real credentials.
3. Ensure the database and sample department/employee data are available.
4. Run the Spring Boot application using your IDE or Maven.
5. Call the three endpoints listed above and inspect the Hibernate SQL logs.

The exact database creation and seed-data mechanism depends on the local project configuration.

## Key Takeaways

- Lazy loading can produce N+1 queries when related collections are accessed across multiple parent entities.
- `JOIN FETCH` explicitly defines the relationship fetch in JPQL.
- `@EntityGraph` defines a fetch plan for a repository operation and can be applied to an inherited repository method.
- Repository method names must follow Spring Data JPA query-derivation conventions.
- Verify behavior with API responses and generated SQL; do not assume an annotation guarantees a specific performance outcome.
